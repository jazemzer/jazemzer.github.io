The initial architecture · 2023

AI Trip Planner's flow

But this is how we managed it.

At the center was the Recommendation Platform and we extended that platform to handle Dialog Management to keep track of conversation history.

When a user sent a message, we first detected the language using a local FastText model. At the time, we only supported English. We then ran moderation checks for things like PII, inappropriate content, prompt attacks, etc.

Once the message passed moderation, we classified the user’s intent across a set of known topics, such as hotels, destinations, attractions, flights and cars. Some topics were not supported yet, so we returned a canned response. For more general questions, we used an LLM to generate an answer.

For recommendation-related conversations, we used a judge to decide whether we had enough information to search. If we were missing key details, an ‘Ask’ step generated the next question for the user, and the conversation continued.

Once the judge determined that we had enough information, an entity-extraction step converted the conversation into structured JSON. We then normalized that structure into the format expected by the Recommendation Platform.

The Recommendation Platform returned the cards used in the carousels we saw earlier. Finally, another LLM summarized those recommendations, generating the supporting text that appeared alongside the carousel cards on UI.

GenAI architecture · 2023

The intial architecture

And this is what the initial architecture looked like.

At the centre was the existing Recommendations Platform. We extended it with conversation orchestration capabilities. It had persistence for dialog management.

The platform was wired up to the frontend via a bunch of gateways and microfrontends.

At the bottom was the OpenAI API. To connect to it, we introduced a thin OpenAI Proxy that acted as an anti-corruption layer, preventing OpenAI-specific types and concepts from leaking into Booking.com’s services.

The proxy also provided a shared interface for cross-cutting capabilities such as centralized monitoring, credential management, billing, and enforcing legal and geographical constraints.

It logged requests and responses to an Amazon S3 bucket with an expiration policy, which enabled offline security scans.

The purple LLM components from the previous slide were implemented by ML scientists as LangChain blocks in a shared Python library. The library connected to the OpenAI Proxy, and the individual steps were exposed as HTTP endpoints to the services above.

This setup allowed the cross-functional team to iterate faster

How the architecture evolved

Three layers of evolution

As the no of usecases grew, we needed new capabilities, and the architecture evolved with them.

Let's look at how that happened across the three layers

1. LLM access and safety: This layer controlled model access & safety checks

2. Shared GenAI capabilities: This layer gave product teams reusable services and libraries

3. Product Orchestration: This layer connected the Genai experience to existing Booking.com capabilities

LLM access and safety

The first layer focused on controlled access to language models and the safety checks around them.

The model-building foundation

We started fine-tuning models

To improve accuracy, latency and cost efficiency

We started fine-tuning models to better adapt them to Booking.com’s domain. For example, our intent classification accuracy was 80% with chatgpt and in-context learning but were were able to push that to 90% with our own fine-tuned model.

The orange blocks show the first set of models we fine-tuned. Apart from improving accuracy, this also helped with reducing cost and latency.

To optimize our fine-tuning setup, we developed a generic LLM training framework that supported various open-source LLMs.

It supported training methods ranging from full-parameter fine-tuning to LoRA and QLoRA, as well as post-training techniques such as Direct Preference Optimization.

The framework also supported distributed multi-GPU training and reusable training pipelines, so teams could apply the same foundation across different models and tasks.

The shared inference layer

GenAI Gateway

An unified interface for 3rd-party and in-house models

As we started building our own fine-tuned models and experimenting with other foundational models, we replaced the OpenAI Proxy with a robust GenAI Gateway.

It provided a single governed way to call LLMs both the foundational models and Booking's own fine-tuned open-source models.

It handled all the cross-cutting needs like model routing, rate limiting, cost tracking, security, observability, content moderation, PII redaction, etc.

It also had access to AI registry.

After AI Trip Planner went to production, we began running experiments with different model versions & prompt variants.

And as the portfolio grew, we needed a system of records to help with governance, discoverability and re-use. That's where AI registry came in.

The AI Registry acts as a catalog for our AI assets, tracking things like versions, ownership and lineage. We started with models and prompts, but it has since then expanded to include agents, workflows, tools and even applications.

The shared agent runtime

Agent Serving Platform

A platform to build and run agents

We built a shared agent runtime where teams could deploy custom agents. It took care of the horizontal concerns around packaging, containerization, deployment, scaling, runtime isolation and security.

It also connected to the systems we saw earlier: the GenAI Gateway for model access, the Toolbox Platform, the AI Registry and observability.

We created an SDK for building and deploying custom agents. It provided an abstraction over open-source agent SDKs, together with connectivity to Booking.com systems.

The platform also included reusable general-purpose agents that teams could customize through configuration. For teams that needed deeper customization, it provided an opinionated framework for building agents according to internal standards.

Traditional software systems could access these agents through a client SDK. Requests flowed through a gateway that handled cross-cutting concerns such as routing and traffic management.

Finally, the platform supported the A2A protocol, allowing agents to discover and call one another.

The shared platform

Other foundational systems

Supporting services behind reliable agent execution

We also built a few platform services to support reliable agent execution.

First, short-term memory helped agents maintain ephemeral context. It acted like a scratchpad or working memory, allowing them to remember information across interactions.

Second, the Embedding Service abstracted the generation, storage and retrieval of embeddings.

Finally, the RAG service provided configuration-based Retrieval-Augmented Generation out of the box.

The next platform concern

Evaluations

Ensuring reliability in a probabilistic world

Since agents are probabilistic, we wanted a systematic way to test and improve their behaviour and reliability.

That brings us to evaluations.

LLM as a judge

Using an LLM to judge the output of another LLM

Reference: Confident AI — Why LLM-as-a-Judge Is the Best LLM Evaluation Method

Traditional software tests are not sufficient because agent responses are open-ended and there is no single correct answer.

So, we used one LLM to evaluate the output of another LLM.

Evaluation design

The building blocks of evaluation

We defined evaluation criteria such as relevance, accuracy, completeness and tone, then trained a judge LLM to score each response against those criteria.

Evaluations

The evaluation stack

To build and evaluate judge LLMs, we needed reliable golden datasets. So, we created a centralized repository of internal and external benchmark datasets, with automatic refreshes as new data became available.

When a dataset was too small, we used a synthetic data generator to augment it. To help teams create custom judges for their use cases, we built a self-serve framework and provided a curated library of reusable judges for common evaluation needs.

As the number of available LLMs grew, we needed a consistent way to compare them. We built an automated evaluation framework that continuously tested both commercial and in-house models, then reported their performance in a dashboard. This allowed teams to select models based on data.

We also made it easier for teams to orchestrate evaluations through a shared evaluation framework.

The Dual Loop

Offline and online evaluation

Benchmark before launch and monitor after release

Sources: LLM Evaluation: Practical Tips at Booking.com; OpenAI: Evals drive the next chapter of AI

Evaluation happens in two connected loops.

At the bottom is the familiar product lifecycle.

The inner loop happens before anything ships. Teams write a prompt or build agents, run evaluations, review the quality of the output and refine the application until it meets the required standard. When it meets the bar, it is tested and deployed.

The outer loop starts after launch. Teams monitor quality in production and watch for drift. When behaviour changes or quality drops, they update the prompt or configuration, evaluate the change and ship a new version.

This means evaluation becomes part of both building and operating the product.

Evaluations

The evaluation harness

Automating evalutions at scale

Sources: AI Agent Evaluation; LLM Evaluation: Practical Tips at Booking.com

There are two phases to running an automated evaluation: preparation and execution.

During preparation, the team defines the metrics, chooses the dataset and selects a judge from the catalog. If no suitable judge exists, they build one using the Judge Factory. They then record these choices in an evaluation configuration.

During execution, the runtime loads the configuration and dataset, then invokes the candidate LLM or agent. If the output is already available from a production trace, this inference step is skipped. The judge LLM then scores the output, and the results are analyzed and reported so the team can decide what to improve next.

Architectural evolution

Layer 3 evolution

Product orchestration

The third layer connected GenAI experiences to Booking.com capabilities and product-specific workflows.

The orchestration layer

A dedicated GenAI Orchestrator

Product logic moved into a specialized workflows

As the architecture evolved, we moved conversation and dialog management into its own dedicated system.

We learned that running AI in production involves much more than calling a model. Multiple components need to work together to handle failures, fallbacks and experimentation reliably.

We called these coordinated sequences of steps workflows, and the engine that executed them the GenAI Orchestrator.

Workflows

Orchestration as configuration

A custom DSL to define GenAI workflows as directed graphs

The first workflows were written in a custom DSL, essentially a machine-readable directed graph.

Each node represented an operation, such as calling an LLM, invoking an agent or running a tool. The edges defined the sequence and conditional logic between those operations, while shared state preserved data and context across the graph.

Teams could author and iterate on these workflows through AI Studio, which made product experimentation and refinement much faster.

Orchestration as Configuration

It worked, but it was not perfect.

  • Weak typing
  • Unsafe I/O mappings
  • Execution engine constraints
  • Limited debuggability and observability
The next iteration

So, we optimized it further with
a code-first approach.

The orchestration SDK

Polyglot code-first approach

Using a shared intermediate representation

The code-first approach allowed teams to create workflows using SDKs in Java and Python.

The SDKs generated a shared intermediate representation that supported downstream capabilities such as workflow execution, registration, visualization and OpenAPI specification generation.

We also built a graph transpiler that could read and translate legacy workflow configurations into the same intermediate representation.

The platform evolution

Workflow Orchestration Platform

Moving towards self-service

Next, we evolved the single GenAI Orchestrator into a full-fledged orchestration platform to enable self-service.

Teams could build and deploy their workflows on a shared orchestrator instance or spin up a dedicated orchestrator instance when they needed better isolation and control.

The takeaways

What we learned

Three lessons from building the ecosystem.

What we learned

Start with the product, not the platform

Build first. Learn. Generalize what repeats.

The ecosystem did not begin with a platform blueprint. Product work revealed which capabilities were worth generalizing. AI Trip Planner was the first learning vehicle, and later products made those capabilities reusable.

Build something valuable, learn where the friction is, and generalize only what proves reusable.

What we learned

Reliable AI needs bounded workflows

Limit autonomy to what you can validate

The LLM was never the whole product. In the first Trip Planner, it translated free-form intent into structured calls to existing recommendation and UI systems.

The right solution is often a bounded, evaluated workflow - not an unconstrained autonomous agent

What we learned

Build evaluation into the product loop

Evaluate before and after launch.

Evaluation belongs in both the inner build loop and the outer production loop. Teams refine the system before launch, then monitor quality and drift after launch. That feedback shapes both the next product iteration and the next platform capability.
